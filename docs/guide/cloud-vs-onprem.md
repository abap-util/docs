# Cloud vs. On-Premise

`abap-util` is designed so the same calling code works in three environments. This page explains where the differences sit so you can make informed choices when consuming the library.

## What's identical

`zabaputil_cl_util_context` and the other classes compile on ABAP Cloud, Standard ABAP and NetWeaver 7.02 from one source — strings, JSON, XML, RTTI, time, URL, filters, messages, HTTP, logging, GS1 barcodes, parallel processing and most other helpers work the same everywhere.

## Where the implementation differs

Some helpers need APIs that only exist in one world. There are no separate adapter classes for that: those methods branch at runtime with `check_abap_cloud( )` and reach the environment-specific API through a dynamic call, so the class still compiles everywhere — for example released cloud APIs (`xco_*`, `cl_web_http_*`) on ABAP Cloud and classic APIs (function modules, `cl_http_client`) on Standard ABAP.

## Methods that need Standard ABAP

These methods have no ABAP Cloud counterpart. They compile on ABAP Cloud, but raise `zabaputil_cx_util_error` when called there:

| Area | Methods |
| --- | --- |
| [Long Texts](/api/longtext) | `longtext_read`, `longtext_save`, `longtext_delete` |
| [RFC](/api/rfc) | `rfc_call_dynamic` |
| [MIME, Spool & Forms](/api/mime) | `mime_read`, `mime_save`, `spool_get_pdf`, `form_get_pdf` |
| [Report Variants](/api/variants) | `variant_list`, `variant_read` |
| [ABAP Messaging Channels](/api/amc) | `amc_send` |
| [Attachments (GOS)](/api/gos) | `gos_attach`, `gos_list`, `gos_read` |

`rfc_ping` and `rfc_check_destination` work on both: on ABAP Cloud they take the name of a BTP destination. `parallel_run` uses `CL_ABAP_PARALLEL` where it exists and runs the tasks sequentially otherwise.

## Methods that intentionally differ in behavior

| Method | Cloud | On-Premise |
| --- | --- | --- |
| `zabaputil_cl_util_http->set_session_stateful` | No-op (feature not released) | Calls `set_session_stateful` on the HTTP server |
| `zabaputil_cl_util_http->get_response_cookie` / `delete_response_cookie` | No-op (no released counterpart) | Reads/deletes the cookie from the on-prem response object |

If a feature only exists on one side, the documentation page for that feature calls it out explicitly.

## Detecting the environment at runtime

```abap
IF zabaputil_cl_util_context=>check_abap_cloud( ) = abap_true.
  " Running on ABAP Cloud
ELSE.
  " Running on Standard ABAP
ENDIF.
```

Use this only when you have a genuinely different code path — most of the time the helpers above already abstract the difference for you.

## HTTP — one handler, two factories

The HTTP wrapper exposes a single object with the same instance methods regardless of where it runs. Just pick the right factory:

```abap
" On-Premise (e.g. SICF handler implementing IF_HTTP_EXTENSION)
DATA(lo_http) = zabaputil_cl_util_http=>factory( server = lo_server ).

" ABAP Cloud (e.g. handler implementing IF_HTTP_SERVICE_EXTENSION)
DATA(lo_http) = zabaputil_cl_util_http=>factory_cloud( req = lo_req res = lo_res ).

" Identical from here on
DATA(ls_req) = lo_http->get_req_info( ).
lo_http->set_cdata( '{"ok":true}' ).
lo_http->set_status( code = 200 reason = 'OK' ).
```

## Persistence (`zabaputil_cl_util_db`)

The persistence service uses table `ZABAPUTIL_T_91`. The table is shipped in the on-premise / Standard ABAP package only. On ABAP Cloud, persistence on this table is not currently supported — use the BTP ABAP Environment's recommended persistence patterns (e.g. business object behavior implementations) for new development.

## Down-port to NetWeaver 7.02

The 7.02 branch is generated by the `auto_downport` workflow (see [Compatibility](./compatibility)). The downport keeps the public API but rewrites:

- `DATA(...)` declarations into explicit `DATA` + `MOVE`
- inline `VALUE #(...)` expressions into table appends
- string templates (`|...|`) into `CONCATENATE`

Your calling code can still use modern ABAP if your system supports it; only the library itself is rewritten.
